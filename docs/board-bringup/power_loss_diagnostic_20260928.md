## 结论

本次原因尚未锁定。没有取得关机前的温度曲线、内核崩溃记录或板端 5V 波形，不能认定为过热，也不能认定为供电掉电。

用户确认：异常时红灯熄灭，拔插 USB 后恢复；没有连接风扇。供电来源、额定电流和是否安装散热片尚未确认。

用户手册说明板上只有一个红色 LED，由软件控制，内核启动后闪烁。当前 status_led 的 trigger 为 heartbeat。因此，红灯停止闪烁/熄灭也可能来自系统卡死，不能单凭灯的状态判断 5V 输入已经消失。

## 温度与风扇

| 温区 | 系统配置的 critical 阈值 |
|---|---:|
| CPU 大核/小核 | 110°C |
| DDR / NPU / GPU | 110°C |
| skin_zone | 50°C |

CPU 55°C、90°C 的另外两个阈值类型为 passive，不能把 55°C 的散热控制触发点当成关机阈值。当前 skin_zone 也低于其 critical 阈值。这些是系统配置值，不是推荐工作温度，也不能代表 PMIC 的硬件保护阈值。

日志持续出现 PD5 引脚占用、PWM 通道 5 启用失败和 cooling_device9 无法设置 PWM。已追到系统自带 /usr/lib/orangepi/orangepi-hardware-optimization 的 orangepizero3w 分支：它导出 GPIO101（PD5）并置高，与内核 pwm-fan 使用同一引脚。用户没有接风扇，这些报错不能作为本次关机原因，也不能据此认定风扇故障。未改动该脚本、设备树或热保护配置。

## 为什么没找到上次最后的报错

- journald 设置 Storage=volatile；journalctl --list-boots 只有本次启动。
- /var/log 位于 /dev/zram1 内存盘，掉电后末尾日志会丢失。
- /var/log.hdd 有磁盘备份，但备份 syslog 最后停在 UTC 13:14:08 左右，早于 UTC 13:47:56 的异常。备份未覆盖最后约 34 分钟。
- /sys/fs/pstore 未提供可读崩溃记录。
- 启动早期时钟未同步，wtmp/启动日志中的 13:17 时间不能直接当成实际重新上电时间。
- 当前日志中部分 “Reached target Shutdown” 来自 SSH 会话退出时的用户 systemd 实例，不是 systemd[1] 的整机关机证据。

本次采样写入 /home/pi/drone_project/logs/power_20260928，并逐条 flush/fsync；该目录位于 SD 卡根分区。日志和报告同时复制到本机 F 盘。

## 下一步判别方法

1. 先确认供电。用户手册建议固定 5V/3A Type-C 电源，供电接口不支持 PD 协商。若目前由电脑 USB 供电，换符合手册要求的独立电源和短供电线，再进行相同操作比较。
2. 测量异常时开发板输入端 5V 是否消失或跌落；需要捕获瞬态，正常空闲时万用表测到 5V 不能排除负载瞬间掉压。模块 LDO 有电压也不能单独证明整板供电稳定。
3. 对同样操作同步记录温度。如果电源稳定且断联前温度持续逼近 critical 阈值，过热假设才有更强证据。当前未做压力测试。
4. 若需要抓卡死/内核错误，用手册的 DEBUG 串口、115200 波特率记录。此前 COM25 对应的 UART7 并没有捕获到内核控制台，不能用它的空日志排除崩溃。
5. 可以再次运行 scripts/power_diagnostics/power_monitor.py，选择一个新的 logs 输出文件；监测有时长上限，不会修改系统配置或设置开机启动。
