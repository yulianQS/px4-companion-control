# 板端工程日志与保留规则

日志保存在 `/home/pi/drone_project` 内，不自动清理、不覆盖历史文件，不更改系统挂载或时间配置。旧文件名称和格式保留；以下规则用于新记录。

## 文件位置

| 类型 | 目录及示例 | 记录范围 |
| --- | --- | --- |
| 比赛任务事件 | `mission_runs/mission_20261023T134500.123Z_b12345678_p2000_n0.jsonl` | 本次完整任务定义、启动、积木切换、控制命令、搜索证据、停止及最终结果 |
| 飞行 CSV | `flight_records/flight_20261023T134459.123Z_b12345678_p2000_n1.csv` | 从收到解锁心跳到确认上锁；独立于任务数量，可包含多次任务或手动控制 |
| 启动与进程输出 | `logs/runtime/<启动会话>/<启动会话>-control.log`、`-web.log`、`-vision.log` | 控制、网页、视觉 stdout/stderr；每个组件有同名 `.json` 元数据 |
| 启动索引 | `logs/runtime/<启动会话>/session.json` | 启动时间、boot ID、沿用已有进程还是新启动、组件日志位置与启动结果 |
| ROS 原生日志 | `logs/runtime/<启动会话>/ros/` | 经 `start_runtime.py` 启动的 ROS launch/node 日志，与视觉控制台输出一起定期落盘 |
| 单独启动视觉 | `logs/ros/<时间戳与启动标识>/` | 经 `start_vision.sh` 单独启动的视觉输出及 ROS 原生日志 |
| 性能记录 | `logs/performance/<时间戳与启动标识>-<标签>/` | `metadata.json`、`threads.csv`、`system.csv`、`summary.json`，可选 `htop.typescript` |

启动会话格式为 `20261023T134500.123456Z_b12345678_p2000_随机标识`。任务和 CSV 使用时间戳、boot ID 前八位、PID 与进程内递增编号；创建时排他检查，重复名称不会覆盖旧记录。性能文件位于带时间戳的独立目录内，内部文件名称保持原有约定。

所有文件名的 `Z` 明确表示 UTC；北京时间为 UTC+8，例如 `13:45Z` 对应北京时间 21:45。时间取自板端系统时钟；没有自动修改系统时钟。板端时钟未校准时，日期可能不准确，不能仅凭文件名跨开机推断先后顺序。

## 如何关联一次飞行

1. 从运行监控区取得任务日志名称和飞行 CSV 名称，或查看相应目录。
2. 任务 JSONL 第一行 `configuration` 保留实际执行的任务图，并记录 `run_id`、`boot_id`、`utc_iso`、`monotonic_s`、`runtime_session` 和启动时已有的 `flight_log_file`。
3. 每个任务事件都记录 UTC、单调时钟、boot ID 和 run ID。CSV 保留原有全部列，在末尾增加 `monotonic_s`、`boot_id`、`runtime_session`。
4. 同一 boot ID 内按 `monotonic_s` 对齐事件和 CSV，不直接比较各自从零开始的 `elapsed_s`。系统时钟跳变不影响单调时钟。跨开机的单调时钟不能直接相减。
5. 一个 CSV 对应一次解锁会话，不必与某个任务一一对应。任务启动时尚未收到记录线程的文件信息时，`flight_log_file` 可能为空；仍可按 boot ID 和时间范围对应。

经启动脚本新建的进程继承 `runtime_session`。启动脚本发现已有进程时保留它们，不为了记录日志而重启飞控；这些进程仍属于它们原来的会话。

## 完整、中断和落盘

- 任务运行时为 `.partial.jsonl`；调度收尾并写入 `run_finished` 后，等待日志线程排空、`flush + fsync`，再改为 `.jsonl` 并同步父目录。任务成功、失败、用户停止由最终事件区分，文件完整不代表任务成功。
- 飞行运行时为 `.partial.csv`；确认上锁后同步文件并转为 `.csv`。链路中断或服务正常退出而未确认上锁时，归为 `.interrupted.csv`。
- 新版服务启动会检查新版文件名中的 boot ID 和写入进程。之前开机或写入进程已消失的 `.partial` 记录归为 `.interrupted`，保留原数据；不会把仍有写入进程的文件归档。无法可靠识别写入者的历史 `.partial` 文件保持原样，需人工核对。
- 任务与 CSV 的常规落盘检查约每秒一次，分别由日志线程执行；飞控 20 Hz 输出线程不做同步写盘。文件完成后的重命名也会同步父目录。
- 运行输出由独立日志进程保存，每秒检查落盘，正常退出时写入返回码与结束时间。异常断电后，原输出保留；下次通过 `start_runtime.py` 启动时，将已消失的日志进程元数据标记为 `interrupted`。
- 性能 CSV 每次采样落盘，正常结束写入摘要；可捕获的异常退出在 metadata 标记中断。ROS 原生日志通过视觉输出日志进程定期同步。
- 存储失败会在任务状态 `log_error`、CSV 状态 `error` 或进程元数据中体现。网页运行监控显示任务/CSV 保存异常。记录失败不等同于任务失败，不能用文件存在来判断已保存完整。

`fsync` 提高突然断电时的可恢复性，但不保证断电瞬间及尚在队列中的数据全部保留；异常文件末尾也可能是不完整行。存储卡或文件系统故障同样可能导致同步失败。不要将部分文件或缺少结束事件的日志当成完整运行证据。

## 启动和历史记录

推荐仍使用 `scripts/start_runtime.py` 或 `scripts/start_console.sh`，它们会同时保存进程输出。直接执行控制二进制仍会记录任务及 CSV，但终端 stdout/stderr 只有经日志包装器启动才会被归档。ROS/系统自身已有历史目录不移动、不清理。`/dev/shm/drone_vision` 的状态和最新图片是运行缓存，不是历史日志，也不连续录制视频。

本次改动不删除历史日志、不设置自动保留天数，不修改 PX4 自身存储卡日志或系统 journal。需要释放空间时先导出归档，再显式选择要删除的记录。
